# Kickoff meeting script

## Context

Our problem-space sentence: a company that sends prompts to external LLM providers needs per-company policy on what may leave the building and what may come back, and no existing gateway lets them shape that policy without adopting someone else's rules.

We believe the product is the plugin system itself, not data filtering — filtering, access control, logging and routing are all plugins on top of it. We have not checked whether an IT department will actually write those plugins, and we do not know whether the customer will accept restart-only plugin loading instead of loading on the fly.

This meeting has to settle five things: whether the plugin system is the product, which hook points plugins must reach, how plugins are installed and written, who holds the provider tokens, and what the first runnable version looks like. The two questions that would change the project most if the answer went the other way are 1 and 9.

## Questions

**Product vision and scope**

1. _(closed)_ Is the product the plugin system itself, with filtering as one example plugin, or is filtering the product?
2. _(open)_ When this works, what is different about how a company controls what reaches an LLM?
3. _(closed)_ Is the simplicity of creating new plugins the core value of the project?

**Plugin capabilities and hook priorities**

4. _(closed)_ Can a plugin analyze the LLM response as well as the user request?
5. _(open)_ What about routing — should the gateway choose a model for a request?
6. _(open)_ How many plugins do you expect to run in the gateway at the same time?

**Plugin loading and implementation language**

7. _(closed)_ Is it acceptable to restart the gateway after installing a plugin?
8. _(open)_ Will the plugins be generated by coding agents, and should the tests be too?
9. _(open)_ What language should the gateway and plugins be written in — is a custom domain-specific language acceptable?
10. _(closed)_ Would a guide or skill for coding agents on writing plugins be useful?

**Authentication and provider tokens**

11. _(open)_ Should the server hold the provider tokens, or proxy requests with the users' own tokens?
12. _(closed)_ Do we store tokens on the server or contact a token management system?
13. _(open)_ Should users be able to bring their own provider tokens?

**MVP scope, timeline and ways of working**

14. _(open)_ What is the first stage — something that works — and when can you deliver it?
15. _(open)_ How many LLM API types should we support?
16. _(closed)_ The course allows any AI tool; our work will be more about validating agents than coding. Is that okay?
17. _(closed)_ Is there a follow-up meeting, and where do we ask further questions?

## Key improvements

**"Do you want a plugin system?" -> "Is the product the plugin system itself, with filtering as one example plugin, or is filtering the product?"**

The original asks the customer to endorse our idea, which invites a polite yes. The rewrite forces a choice between two readings of the original description, so the answer settles the vision instead of confirming it. The principle: ask for a decision between concrete alternatives, not for approval.

**"Is Java fine for you?" -> "What language should the gateway and plugins be written in — is a custom domain-specific language acceptable?"**

The original pushed our preferred answer and hid the real question, which was whether a new plugin language was on the table at all. The rewrite opens the space and names the risky option, so the customer's objection to a domain-specific language comes out on its own. The principle: do not anchor the customer to your preferred option; surface the option you expect them to reject.

**"Can plugins run without restarting?" -> "Is it acceptable to restart the gateway after installing a plugin?"**

The original framed restart as a limitation to be avoided, so any answer would sound like a concession. The rewrite offers restart as the default and asks whether it is acceptable, which matches how the customer actually thinks about a server-side program. The principle: state your assumption as the baseline, so disagreement is the only thing that needs saying.
