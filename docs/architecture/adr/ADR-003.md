# ADR-003: Expose plugin management as a Gateway HTTP API consumed by a thin CLI

**Status:** Accepted
**Containers:** CLI, Gateway, Plugin Manager, prototype gateway
**Addresses:** FR-01, FR-02, FR-03, FR-04, FR-05, FR-009, QR-01, QR-03, QR-05
**Decision:** The Gateway exposes a plugin management HTTP API with endpoints for upload, list, enable, disable, and delete; the CLI is a thin client over this API. The Gateway writes uploaded plugin files and desired configuration to the shared volume; the Plugin Manager loads saved changes at startup.

## Context and Problem Statement

DevOps needs a repeatable, scriptable way to manage plugins. Letting the CLI write directly to the shared volume would bypass validation and couple the CLI to the storage layout. Every management operation must be observable and testable over HTTP.

The 2026-10-25 discussion considered whole-config GET/POST: the CLI would act as a remote text editor. But even with a typed request, it would have to fetch the config, change one part, and submit the whole document again. An edit made in between could be lost.

## Considered Options

1. **CLI writes directly to the shared volume** — rejected: bypasses validation, couples the CLI to the storage layout, and leaves no single source of truth for the registry.
2. **CLI talks directly to the Plugin Manager** — rejected: creates a second entry point and splits management state across two services.
3. **Gateway exposes a plugin management HTTP API; the CLI is a thin client** — chosen. A single entry point for management, validation in one place, testable over HTTP.

4. **Whole-config GET/POST, untyped or typed** — rejected: plugin-specific commands would need client-side read-modify-write logic. Typed input alone does not prevent stale overwrites.
5. **Whole-config replacement with ETags** — can reject stale writes, but adds conflict handling that targeted operations do not require; not implemented.

## Decision Outcome

Chosen option: **Option 3 — Gateway HTTP API with a thin CLI**, because it keeps the Gateway as the single control point and makes every management operation testable with standard HTTP tooling.

The prototype implements these operations in its [management API](../../api/plugin-management.md), including options replacement and relative ordering. The Gateway owns the saved files; its PluginManager class is part of the same process, not a separate service.

GET shows what is running. Write responses confirm what was saved for the next startup. The CLI remains planned.

### Consequences

- **Good:** All plugin operations go through one API; the CLI is replaceable; acceptance tests can drive the API directly.
- **Bad:** The Gateway carries both data-plane and control-plane responsibilities; a Gateway outage blocks plugin management.
- Targeted changes preserve unrelated configuration, but two PUTs to the same plugin's options remain last-write-wins. The prototype serializes API writes in one process and rejects detected external TOML edits; concurrent file editors and multiple workers remain unsupported.
- **Quality attributes accepted:**
  - Performance Efficiency / Time Behaviour (QR-01) — management endpoints share the Gateway's HTTP stack.
  - Maintainability / Testability (QR-03) — the API is exercised by integration tests without the CLI.
  - Reliability / Fault Tolerance ([QR-05](../../quality-requirements/qr/QR-05.md)) — recoverable write failures preserve saved state without changing the running pipeline; this is not a crash-recovery guarantee.
