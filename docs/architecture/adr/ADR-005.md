# ADR-005: Authorize administration independently of request plugins

- **Status:** Accepted
- **Created:** 2026-10-25
- **Updated:** 2026-10-25
- **Containers:** `prototype gateway`
- **Addresses:** [FR-008](../../functional-requirements/fr/FR-008.md), [QR-04](../../quality-requirements/qr/QR-04.md)

## Context

The feature explicitly requires separate admin authorization.
Administrators can upload executable Python and disable the chat authentication plugin; ordinary chat credentials must not grant those powers.
The credential separation is explicit; the options below document the implementation's implied boundary.

## Considered Options

- A router-level bearer check using a separate admin key.
- Reuse the gateway key: every chat client could modify executable code and policy.
- Put administration behind the authentication plugin: disabling or reordering that plugin could remove admin protection.
- Add an identity service and role-based access: useful for production, but outside the prototype's simple credential model.

## Decision Outcome

Chosen option: protect every admin route with `GATEWAY_ADMIN_API_KEY`, independently of the middleware chain.
Use a different value from `GATEWAY_API_KEY`; the code does not enforce that the two environment values differ.
Missing or invalid admin credentials return 401 for valid-shaped requests; an unset admin key disables administration with 503.
The comparison is constant-time and the router remains protected when chat authentication is disabled.

## Consequences

- Security / Authenticity ([QR-04](../../quality-requirements/qr/QR-04.md)): distinct configured credentials separate chat callers from administrators.
- One shared admin credential provides no individual identity, roles, or per-user audit trail.
- Trusted plugins have full process access. Router authorization is not a sandbox against installed code; protect the key and restrict network access, using TLS outside localhost.
