# ADR-001: Split the system into CLI, Gateway, and Plugin Manager with a Java/Python stack

**Status:** Accepted
**Containers:** CLI, Gateway, Plugin Manager
**Addresses:** FR-01, FR-02, FR-03, FR-04, FR-05, FR-06, FR-07, QR-01, QR-02
**Decision:** Run the product as three deployable containers — a Python CLI, a Java Gateway, and a Python Plugin Manager — that communicate over HTTP; plugin files live on a shared volume mounted into the Gateway and the Plugin Manager.

## Context and Problem Statement

The gateway must accept LLM requests, route them through a configurable plugin chain, and allow DevOps to manage plugins without redeploying the core. A single-process design would couple plugin execution to the Gateway lifecycle and make isolated plugin failures fatal. The team needs a split that separates the request path (Gateway) from plugin execution (Plugin Manager) and a management path (CLI), while keeping plugin files in one place both services can reach.

## Considered Options

1. **Single Java process with embedded Python via GraalVM** — one container, no HTTP boundary. Rejected: a plugin crash would take down the Gateway, violating QR-02; plugin isolation is lost.
2. **Gateway and Plugin Manager merged into one Python service** — simpler deployment. Rejected: loses the Java ecosystem for high-throughput HTTP handling and puts the request path and plugin execution in the same failure domain.
3. **Three containers — CLI (Python), Gateway (Java), Plugin Manager (Python) — plus a shared volume for plugin files** — chosen. Separates concerns, isolates plugin failures from the Gateway, and lets DevOps manage plugins over HTTP.

## Decision Outcome

Chosen option: **Option 3 — three containers with a shared plugin volume**, because it directly supports QR-02 (plugin failure does not terminate the Gateway) and QR-01 (Gateway latency under load), while keeping the plugin lifecycle independent of the Gateway process.

### Consequences

- **Good:** Plugin crashes are contained in the Plugin Manager and handled by the Gateway's failure policy. The CLI and the management API can evolve independently. The shared volume gives both services one source of plugin files.
- **Bad:** An extra HTTP hop between Gateway and Plugin Manager adds latency; three units to operate instead of one; the shared volume is a single point of plugin-file storage.
- **Quality attributes accepted:**  Functional Suitability / Functional Completeness (QR-01) — the Gateway invokes the full enabled plugin set on every request and response.
