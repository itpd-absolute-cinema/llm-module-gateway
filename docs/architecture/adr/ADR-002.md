# ADR-002: Apply plugin changes by restarting the Plugin Manager, reading plugin files from the shared volume

**Status:** Accepted
**Containers:** CLI, Gateway, Plugin Manager, prototype gateway
**Addresses:** FR-01, FR-02, FR-03, FR-04, FR-05, FR-06, FR-009, QR-02, QR-03, QR-05
**Decision:** Plugin files are written to the shared volume through the Gateway's management API; the Plugin Manager scans the volume on startup and loads plugins according to their saved enabled state, options, and order. Applying an uploaded plugin requires restarting only the Plugin Manager, not the Gateway.

## Context and Problem Statement

DevOps uploads a single-file plugin through the CLI and expects it to participate in request processing. Hot-reload adds complexity the team does not need: a controlled restart of the Plugin Manager is acceptable and keeps the Gateway serving throughout. The system must keep the Gateway available while plugin state changes.

The restart boundary follows [DEC-001](../../decisions.md#dec-001-hot-reload-ruled-out). The prototype has no separate Plugin Manager process, so it requires restarting the whole gateway.

## Considered Options

1. **Hot-reload in the Plugin Manager (watch the volume at runtime)** — chosen against: adds a watcher, a reload protocol, and race conditions; no benefit when a restart is acceptable.
2. **Rebuild the whole image and redeploy every service on each plugin change** — rejected: too heavy, takes the Gateway down for a change that only affects plugin execution.
3. **Shared volume + restart only the Plugin Manager** — chosen. The file lands on the volume, the Plugin Manager restarts, scans, and registers; the Gateway keeps serving and applies its failure policy while the Plugin Manager is down.

4. **Rebuild factories after each API update** — rejected in the prototype review: factories have no safe-reinitialization or cleanup contract, and repeated side effects cannot be rolled back.

## Decision Outcome

Chosen option: **Option 3 — shared volume with a Plugin Manager restart**, because it is the simplest way to apply a plugin change while preserving Gateway availability and the QR-02 failure policy.

The Gateway writes the configuration. A running Plugin Manager keeps the configuration it loaded at startup; it does not rebuild factories when an administrator saves a change.

This follows the same principle as replacing a Kubernetes pod: start a new instance with the new configuration, direct traffic to it, and drain the old instance. That is an analogy for a future deployment workflow, not a capability of this prototype. Here, Gateway and Plugin Manager share one process, and the operator restarts it explicitly.

GET reports running configuration with a per-plugin `restart_required` flag. The `X-Restart-Required` header summarizes pending changes for the process. A running plugin must still be disabled, followed by a restart, before it can be deleted.

### Consequences

- **Good:** No hot-reload machinery. The Gateway stays up during plugin changes; requests during the Plugin Manager restart are handled by the failure policy.
- **Bad:** A plugin change needs an explicit Plugin Manager restart; in-flight plugin calls during the restart fail and are governed by the failure policy. The prototype instead restarts its entire process; neither case guarantees uninterrupted requests. Factory-specific validation happens at startup, so invalid saved settings can prevent the next startup.
- **Quality attributes accepted:**
  - Reliability / Fault Tolerance (QR-02) — the Gateway survives the Plugin Manager restart.
  - Maintainability / Testability (QR-03) — the load-and-register path is testable end-to-end.
  - Reliability / Fault Tolerance ([QR-05](../../quality-requirements/qr/QR-05.md)) — prototype administration leaves the running chain unchanged even when saving fails.
