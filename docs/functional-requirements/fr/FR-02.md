# FR-02: DevOps lists all plugins and their statuses through the CLI

**Status:** Active
**Traces to:** Main goal "Allow new plugins to be integrated without redesigning the entire gateway"; observability of plugin state
**Containers:** CLI, Gateway, Plugin Manager

## Behavior

1. The CLI **shall**, when a DevOps engineer runs `cli plugin list`, request the full plugin list from the Gateway's plugin management API.
2. The Gateway **shall** list installed, configured, or active local plugins alphabetically,
   returning `{name, enabled, options, restart_required}` for each plugin.
   Status and options **shall** reflect the Plugin Manager's enabled startup snapshot;
   inactive plugins **shall** return `enabled: false` and `options: {}`.
   The per-plugin restart flag **shall** compare presence, options including value types,
   and numeric position in the saved enabled chain with the startup chain.
   The Gateway retains ownership of saved writes to the Plugin Store.
3. The CLI **shall** display the returned list in a readable table with one row per plugin.

## Acceptance Criteria

### AC-01: Empty registry returns an empty list

With no plugins uploaded, run `cli plugin list`. The CLI prints a header row and no data rows, and exits with code 0.

### AC-02: Status reflects running state

Upload two plugins, enable one via `cli plugin enable <name>`, then run `cli plugin list`.
Before restart, both show `disabled` with empty options; only the plugin saved as enabled has
`restart_required: true`. After restart, that plugin shows `enabled` with its startup options
and `restart_required: false`. The other remains disabled, with empty options and no restart required.
Listing changes neither saved state nor the running pipeline.
