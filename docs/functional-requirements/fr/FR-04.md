# FR-04: DevOps disables a plugin by name through the CLI

**Status:** Active
**Traces to:** Main goal "Enable configurable policies"; operational control over active plugins
**Containers:** CLI, Gateway, Plugin Manager

## Behavior

1. The CLI **shall**, when a DevOps engineer runs `cli plugin disable <name>`, send a disable request for that plugin name to the Gateway's plugin management API.
2. The Gateway **shall** save the named plugin as `disabled` in the Plugin Store, retaining its source and options and, unless explicitly moved, its configured position. The running pipeline **shall** remain unchanged until runtime restart, when the Plugin Manager excludes the disabled plugin.
3. The Gateway **shall** return an error if no plugin with that name exists, and a success response otherwise.

## Acceptance Criteria

### AC-01: Disabled plugin stops affecting requests

Enable a blocking filter plugin, restart the plugin runtime, and confirm a request is blocked. Run `cli plugin disable <name>` and send the same request; it remains blocked until another runtime restart, after which it passes through to the LLM provider.

### AC-02: Status is persisted across requests

After disabling a running plugin, run `cli plugin list`. It still appears as `enabled` with its
startup options and `restart_required: true` until runtime restart. After restart, it appears as
`disabled` with empty options and `restart_required: false`. The saved disabled state, options,
and configured position remain after restart.
