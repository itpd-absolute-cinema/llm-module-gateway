# QR-05: Preserve Runtime And Saved State During Failed Updates

Admin updates leave the running pipeline unchanged and invoke no plugin factories, while recoverable configuration-replacement or plugin-file-write failures preserve the previous saved state.

- **Status:** Active
- **Characteristic:** Reliability
- **Sub-characteristic:** Fault Tolerance
- **Business importance:** Medium
- **Technical risk:** High

## Scenario

### Source

An authorized administrator and a test harness injecting recoverable storage errors.

### Stimulus

Upload, options replacement, enabled-state changes, and inactive-plugin deletion succeed or encounter a configuration-replacement error; upload also encounters a partial source-file write error.

### Environment

One `prototype gateway` process serves a deterministic local responder, with no concurrent external file edits and with rollback operations available.
[DEC-001](../../decisions.md#dec-001-hot-reload-ruled-out) permits restart-only changes.
This scenario excludes distributed writers, power loss, process crashes, and failed rollback; the course schedule in [CON-01](../../product-vision.md#con-01) motivates that limited scope.

### Artifact

The active request pipeline, saved plugin configuration, plugin source files, and administration's saved-state view.

### Response

The gateway shall retain the active handler and avoid plugin imports and factory invocations during every admin update.
On the injected I/O error, it shall report failure and preserve the previous saved state, removing partial uploads or restoring staged deletions as needed.

### Response Measure

Before restart, every attempted update preserves handler identity, deterministic chat output, and import/factory event counts, with zero additional events.
Each injected storage error returns 500; configuration bytes, existing source bytes, GET results, and restart-required state equal their pre-request snapshots, with no new plugin or temporary save file remaining.
After removing the fault, retrying the operation succeeds; its runtime effect occurs only after restart.
Any changed runtime observation, retained partial update, or failed retry fails the scenario.
