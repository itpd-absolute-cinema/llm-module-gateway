# QR-03: Testability of the frontend entry point and plugin loading path

**Characteristic:** Maintainability / Testability
**Business Importance:** High
**Technical Risk:** Medium

**Outcome:** A DevOps engineer can load a new single-file plugin through the CLI and cover it with an automated integration test within one working day, by adding one plugin file and modifying at most one source file.

## Quality Attribute Scenario

| Part | Value |
| --- | --- |
| Source | A DevOps engineer using the CLI |
| Stimulus | Uploads a new single-file plugin through the CLI |
| Environment | Development environment with the documented test command; Gateway and Plugin Manager running |
| Artifact | Gateway entry point |
| Response | The Gateway accepts the plugin, the Plugin Manager discovers and executes it after explicit enablement and runtime restart, and an integration test exercises the request → plugin → response flow |
| Response Measure | ≤ 1 plugin file added and ≤ 1 source file modified outside the plugin directory; integration test runs in ≤ 60 s; the new plugin is invoked on a request after explicit enablement and a Plugin Manager restart (the whole gateway process in the prototype) |

For the prototype, automated tests shall cover the critical modules `gateway/app.py`, `gateway/admin.py`, `gateway/config.py`, and `gateway/core.py`, including authorization, saved-state changes, startup loading, restart isolation, and recoverable storage failures. From `prototype/`, install pinned dependencies with `uv sync --locked` (which may require network access), then run `.venv/bin/python -m unittest discover -s tests -v` offline using temporary files, disposable credentials, and intercepted upstream calls. All three test modules (`test_plugin_admin.py`, `test_plugin_config.py`, and `test_api_errors.py`) shall run with zero failures, errors, skips, or external calls. These API checks do not establish completion of the planned CLI scenario.


## QRT-01

The CI pipeline runs the full test suite from a clean checkout, covering the critical modules named in this requirement.

**Type:** CI

### Procedure

1. Trigger the product-code CI workflow on a pull request to `main`.
2. The workflow checks out the repository in a clean state.
3. The workflow installs the pinned dependencies.
4. The workflow runs the automated test suite offline, using temporary files, disposable credentials, and intercepted upstream calls.
5. The suite exercises the critical modules named in this requirement, including authorization, saved-state changes, startup loading, restart isolation, and recoverable storage failures.

**Pass when:** The CI run is green, and every test module in the suite passes with zero failures, errors, skips, or external calls.
